ledger · architecture & data flow

记账本 Ledger：整体分层、模块边界与关键链路

一套 Flutter 多端客户端 + Spring Boot 服务端 + MySQL 的记账应用。核心设计是 统计口径全部下沉到 SQL 聚合，客户端只做渲染；所有接口共用统一响应体与 JWT 鉴权。 本文按实际仓库代码绘制，覆盖四条主链路的数据流向。

客户端 Flutter · Dart 3.13 服务端 Spring Boot 3.5.16 · Java 17 存储 MySQL 8.4 接口 16 个 数据表 3 张 仓库实现 2 套 HTTP 端口 9090

关键链路的数据流

每一步都标出发生在哪一层。读法是从上往下：先在客户端发生什么，请求打到服务端后又经过哪些关卡，最后数据落到哪里。

链路 A · 登录与鉴权

Flutter 客户端
Spring Boot 服务端
存储层
  1. 1
    客户端登录页填账号密码；服务器地址可现场改，存进 SharedPreferences
  2. 2
    客户端AuthSession.login → ApiClient POST /api/auth/login，此刻尚无 Bearer
  3. 3
    服务端SecurityConfig 放行 login/register；AuthController 校验 LoginRequest
  4. 4
    服务端AuthService 用 BCrypt 匹配 password_hash；失败抛 40101
    存储users 表按 uk_users_username 命中
  5. 5
    服务端JwtService 签发 HS512 token，TTL P7D，issuer ledger-app
  6. 6
    客户端剥掉统一响应体取 data；token 与 user 落 SharedPreferences，拦截器此后自动加 Bearer
  7. 7
    服务端JwtAuthFilter 校验签名与有效期，注入 AuthUser principal
    存储后续查询一律按 user_id 过滤（如 findByIdAndUserId），杜绝越权
  8. 8
    客户端收到 401 → onUnauthorized 清 token 与 user → 自动退回登录页
    服务端token 过期返回 {code:40100}，HTTP 状态同为 401

链路 B · 记一笔账（写入 → 列表 → 报表失效）

Flutter 客户端
Spring Boot 服务端
存储层
  1. 1
    客户端AddTxnPage 选类型、分类、金额、日期，本地先做一轮校验
  2. 2
    客户端LedgerStore.add → RemoteLedgerRepository.insert → POST /api/txns（带 Bearer）
  3. 3
    服务端JwtAuthFilter 鉴权 → TxnController 的 @Valid TxnRequest 校验字段
  4. 4
    服务端TxnService 调 CategoryCatalog 校验分类归属；金额统一保留两位小数
  5. 5
    存储TxnRepository.save 写入 txn 表；索引 idx_txn_user_day(user_id, day, created_at)
  6. 6
    服务端返回 201 Created 与 TxnResponse（含新分配的 id）
  7. 7
    客户端LedgerStore 把新记录插到列表头部并按 day / createdAt 重排，revision++
  8. 8
    客户端RecordsPage 立刻可见新记录；AnalyticsPage 侦测 revision 变化后重新拉取统计

链路 C · 统计口径与聚合

Flutter 客户端
Spring Boot 服务端
存储层
  1. 1
    客户端AnalyticsPage 选日 / 月 / 年 → LedgerStore.summaryOfMonth、dailyTrend、monthlyTrend、years
  2. 2
    客户端GET /api/stats/summary?from&to · /daily?year&month · /monthly?year · /years

链路 D · 头像与反馈图片（multipart + 落盘）

Flutter 客户端
Spring Boot 服务端
存储层
  1. 1
    客户端file_picker 选图；Web 端拿不到本地路径，只取到 Uint8List 字节
  2. 2
    客户端POST /api/auth/me/avatar，multipart 字段名 file；反馈则是 /api/feedback 的 content + images
  3. 3
    服务端Spring multipart 限额：单文件 ≤2MB、整包 ≤10MB，超限直接 413
  4. 4
    服务端AvatarService / FeedbackService 按 Content-Type 反推扩展名，客户端文件名一律不用
  5. 5
    存储落盘 data/avatars/{userId}.{ext}（换图删旧文件）与 data/feedback/{userId}-{uuid}.{ext}
  6. 6
    存储库里只存文件名：users.avatar、feedback.images —— 路径穿越天然不可能发生
  7. 7
    客户端读头像 GET /api/auth/me/avatar?v=<时间戳>，多带版本号绕开 Flutter 的 ImageCache
    服务端直接返回二进制并带 Cache-Control: no-store，服务端忽略 ?v 参数

横切关注点

这套约定横跨所有接口，四个链路共用同一套机制。

统一响应体

HTTP 状态码与业务码同时给出、互不替代：网关按 HTTP 判断，客户端按 code 分支。

成功
{ code:0, message:"成功", success:true, data:{…} }
失败
{ code:40401, message:"账单 999999 不存在", success:false, data:null }

06

设计取舍与风险点

读懂这七条，就读懂了这套代码为什么长这样。

统计口径下沉到 SQL
口径只有 MySQL 一处定义，客户端不参与计算，因此不会出现"两边算法不一致"。代价是离线仓库必须用 InMemoryStats 复刻同一套口径。
端口用 9090 而不是 8080
本机 Windows 把 TCP 8006–8105 整段保留给 Hyper-V/WSL2，8080 绑不上会直接启动失败。改端口用 SERVER_PORT。
图片落盘，库里只存文件名
文件名由服务端按 Content-Type 生成，客户端传的名字一律不用，因此不存在路径穿越。换头像时删旧文件，不留垃圾。
nginx 同源反代规避 CORS
预览站把 /api 反代到宿主 9090，浏览器与后端同源，不触发预检；换 IP、域名、端口都不用重新 build。
JWT_SECRET 生产必须覆盖
仓库里带的是开发默认值（HS512，至少 32 字节）。上线前用 JWT_SECRET 环境变量替换，否则等于没设防。
反馈写库的顺序是刻意选的
事务回滚不会顺手删掉已落盘的图片，最坏留一张孤儿图；反过来先写库再落盘会留下指向空文件的记录，更难收拾。代码选了前者。
本地仓库只是备用
Sqflite 与 SharedPreferences 两套实现服务离线与单测，线上走的始终是 REST 仓库。两套口径要一起回归。
改表结构要手工补列
initdb 脚本只在数据卷为空时跑一次。改过 schema.sql 后已有库需要手工 ALTER，否则启动时 ddl-auto=validate 直接失败。
依据 ledger-front / ledger-backend 仓库实际代码绘制 · 2026-10-30 类名与路径均可直接全局搜索定位
